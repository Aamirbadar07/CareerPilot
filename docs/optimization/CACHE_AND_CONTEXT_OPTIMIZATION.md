# CareerPilot — Multi-Dimensional Caching & Context Architecture

## Overview

Caching in multi-agent workflows is the most potent tool for zero-cost execution. When unchanged inputs produce identical outputs, avoiding the LLM entirely yields **0 tokens billed, $0 cost, and <1ms latency**. This document details the database caching architecture, cache key design, invalidation lifecycle, and context compression patterns in CareerPilot.

---

## 1. Multi-Dimensional Cache Key Design

In `app/core/llm.py`, cache keys are generated using SHA-256 over a composite canonical tuple:

```python
user = inputs if isinstance(inputs, str) else json.dumps(inputs, sort_keys=True)
key = hashlib.sha256(f"{self.model}\0{schema.__name__}\0{system}\0{user}".encode()).hexdigest()
```

### Key Dimensions:
1. **`self.model`**: Prevents cross-model pollution (e.g. results generated by Gemini Flash are never conflated with outputs from Claude Sonnet).
2. **`schema.__name__`**: Partitions cache namespaces across different agents and output schemas.
3. **`system`**: Protects against stale outputs when system prompts or calibration rules are updated.
4. **`user` (canonicalized JSON)**: `json.dumps(inputs, sort_keys=True)` guarantees dictionary key ordering does not cause false cache misses.

## 2. Database Cache Implementation (`LLMCache`)

### Schema Design (`app/db/models.py`)
```python
class LLMCache(Base):
    __tablename__ = "llm_cache"

    key: Mapped[str] = mapped_column(String(64), primary_key=True)
    profile_id: Mapped[str | None] = mapped_column(String(36), index=True)
    value: Mapped[str] = mapped_column(Text)
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=_now)
```

### Thread Safety & Concurrency
The `DbCache` adapter in `app/db/repositories.py` opens short-lived sessions per read/write, allowing parallel worker threads (e.g. `fit_scorer` evaluating multiple jobs concurrently) to read and populate the cache simultaneously without database lock contention.

## 3. Cache Invalidation & Profile Versioning

In CareerPilot, candidate data is versioned (`profile.version`). Artifacts derived from an older version are automatically invalidated on profile mutation:

```
[ Candidate Uploads Resume v1 ]
       │
       ▼
  Ingest & Parse ──────────► Profile Version 1 Saved
       │
       ├──► fit_report (version: 1)
       ├──► tailored_resume (version: 1)
       └──► coaching_plan (version: 1)

[ User Adds Credential or Edits Skills ]
       │
       ▼
  save_new_version() ──────► Profile Version 2 Saved
       │
       ├──► delete_artifacts("tailored_resume", "coaching_plan")
       └──► Old fit_reports (v1) become stale (current() returns None)
```

- When a candidate's profile is updated (e.g. new certification or revised bullets), `save_new_version()` bumps `profile.version` and automatically drops `tailored_resume` and `coaching_plan` artifacts.
- Older fit reports become stale because `current_fits()` filters by `a.profile_version == profile.version`.
- When a candidate profile is deleted, `delete_profile(db, profile_id)` cascades deletions across `profiles`, `profile_versions`, `artifacts`, and `llm_cache` rows linked to that profile ID.

## 5. Cache Hit Performance

- **Cache Hit Latency**: **< 1.5 ms** (SQL primary key lookup on `key`).
- **Cache Hit Token Consumption**: **0 input tokens, 0 output tokens**.
- **Cache Hit Financial Cost**: **$0.00**.
- **Re-run Acceleration**: A user re-opening a previously analyzed profile or re-visiting job fit scores experiences instantaneous rendering without triggering external model calls.
